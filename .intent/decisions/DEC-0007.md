All SSH socket lifecycle (connect, authenticate, channel streams) is managed in the Electron main process. The renderer holds only an `xterm.js` terminal instance per tab and exchanges raw data with the main process over IPC.

## Rationale

- `ssh2` is a Node.js library — it cannot run in the renderer's browser context
- Keeping sockets in the main process is consistent with how `ssh2` is already used in the Vision Lab remote trainer
- The renderer is sandboxed (`sandbox: false` in the current config, but the pattern should not leak Node primitives through the bridge); raw streams must not be exposed via `contextBridge`
- IPC over named channels with string payloads is the correct abstraction — xterm.js has no dependency on how bytes arrive

## Trade-offs accepted

- Every keystroke goes renderer → main → SSH server → main → renderer. Latency over a LAN connection is imperceptible; over a high-latency WAN it may feel sluggish, but this is the same as any web-based terminal (Wetty, ttyd) and is acceptable for an admin tool
- The main process holds open SSH connections indefinitely until the tab is closed or the app exits; the service must clean up on `app.before-quit`

## Implementation pattern

```
// main process
const sessions = new Map<tabId, ssh2.Client>()

ipcMain.handle('ssh:connect', async (_, { connectionId, tabId }) => {
  const conn = new ssh2.Client()
  sessions.set(tabId, conn)
  conn.on('data', (data) => mainWindow.webContents.send('ssh:data', { tabId, data: data.toString() }))
  // ... connect, open shell channel
})

ipcMain.handle('ssh:input', (_, { tabId, data }) => {
  sessions.get(tabId)?.write(data)
})
```
