The Kora Admin section exposes platform-level entities only (organisations, care homes as entities, platform users). It never surfaces resident records, care data, or raw database connection strings.

## Rationale

Resident data held in Kora (young people, care records, medication, incidents, mood entries, goals, etc.) is sensitive personal data under GDPR. Exposing it in a developer admin tool — even read-only — would be a data minimisation violation (Article 5(1)(c)) because there is no legitimate purpose for an admin tool to display it.

Tenancy database URLs are equally sensitive: they are direct credentials to databases containing care records and must not leave the server.

## What is in scope

- Organisation names, IDs, slugs, contact details
- Care home names, IDs, slugs, org association, provisioning status (DB exists: yes/no)
- Platform user accounts (name, email, role) — not linked to any resident record
- System audit log (operation type, actor, timestamp — no data payloads)
- Docker / service health status

## What is explicitly out of scope

- Young people / resident records (any module under `src/young-people/`, `src/daily-logs/`, `src/medication/`, `src/incidents/`, etc.)
- `TenantDatabase` records including DB URLs
- Any data requiring access to a tenant (home) database

## Implementation

- `packages/kora-client` must have no methods that call resident-data endpoints
- If the Kora API adds an admin-facing aggregate endpoint that includes resident counts, that is acceptable (a count is not personal data); individual records are not
